== Fork Notice: Experimental Development

This repository is an experimental fork of https://github.com/OpenBangla/OpenBangla-Keyboard[OpenBangla Keyboard], maintained independently from the upstream project.

The purpose of this fork is to experiment with a simpler, portable, user-local Linux build and installation workflow, with particular attention to immutable and image-based Linux systems. The goal is to avoid requiring system-wide installation or modifying the host operating system's package database.

The experimental work includes:

* Automatic input-method backend selection: KDE/Plasma uses Fcitx5; other desktop environments use IBus.
* User-local installation under the user's home directory.
* Build dependency isolation using a suitable Toolbox, Distrobox, Podman, or Docker environment where available.
* Persistent source and build caches to avoid unnecessary downloads and rebuilds.
* A simple installation workflow intended eventually to be usable by a graphical installer.

[IMPORTANT]
====
This fork is **experimental**. It is **not an official OpenBangla Keyboard release** and should not be treated as a production replacement for the upstream project.

Parts of the experimental installer and integration work are generated or assisted by AI. The code is reviewed and tested incrementally, but AI-assisted code may contain errors, incomplete assumptions, or regressions. Users should review changes before relying on them.
====

The upstream OpenBangla Keyboard code and its original licensing remain the basis of this project. Changes made in this fork are intended to be clearly separated from upstream functionality wherever practical.

*OpenBangla Keyboard* is an open source, Unicode compliant, Bangla input method for GNU/Linux systems.
It's a full-fledged Bangla input method with typing automation tools, includes many famous typing methods such as Avro Phonetic,
Probhat, Munir Optima, National (Jatiya) etc.

Most features of https://www.omicronlab.com/avro-keyboard.html[Avro Keyboard] are present in OpenBangla Keyboard.
So Avro Keyboard users will feel right at home in Linux with OpenBangla Keyboard.

== Features
* Features a __Top Bar__ like Avro Keyboard for easy configuration.
* Layout Viewer
* Phonetic Keyboard Layout (Avro Phonetic)
  ** 100% compatibility with current Avro Phonetic scheme.
  ** Dictionary support can predict and suggest phonetically similar words with correct spelling on the fly.
  ** Autocorrect feature for numerous commonly mistyped words.
  ** Autocorrect support brings commonly used English words to Bangla (like, Facebook, download etc.) even with their original English spelling.
  ** User can add and edit autocorrect entries.
  ** Support for preview window to see originally typed text right under the cursor.
* Fixed Keyboard Layout
  ** OpenBangla Keyboard comes with Probhat, Munir Optima, Avro Easy, Bornona, National (Jatiya) keyboard layouts out of the box.
  ** OpenBangla Keyboard supports Avro Keyboard Layout files (version 5).
* Typing Automation tools for Fixed Keyboard layout
  ** Automatic vowel forming.
  ** Old style "Reph".
  ** Traditional "-Kar" joining.
  ** Automatic "Chandrabindu" position fixing.


== Installation and User-Local Build

This fork does **not** provide a pre-built binary through `tools/install.sh`. The command is a **build-and-install workflow**.

When you run `tools/install.sh`, it:

. Detects the desktop environment and selects the input-method backend.
. Selects an available isolated build environment.
. Creates or reuses that build environment.
. Installs the build dependencies inside that environment, not on the host.
. Configures the OpenBangla source tree with CMake.
. Compiles the selected backend and the OpenBangla application.
. Stages the compiled files.
. Installs the staged files into the current user's `~/.local` directory.
. Performs basic verification of the user-local installation.

The reason for this design is to make OpenBangla easier to build on different GNU/Linux systems without requiring system-wide packages or root access for the OpenBangla installation itself. This is particularly useful on immutable or image-based systems, but the workflow is **not specific to Dakota, Fedora, or any other single distribution**.

The build dependencies are isolated in an available development environment. The host system is not modified with OpenBangla build packages or system-wide OpenBangla files.

=== Quick Install

From a clone of this repository:

[source,bash]
----
git clone --recursive https://github.com/hasanmuammar/OpenBangla-Keyboard.git
cd OpenBangla-Keyboard
bash tools/install.sh
----

The installer automatically chooses the first available build environment in this order:

. Toolbox
. Distrobox
. Podman
. Docker

For Toolbox and Distrobox, the environment's normal host integration is used. For Podman and Docker, the required source, build, cache, and staging directories are made available to the build container.

The installer does not ask the user to choose a build environment.

=== Backend Selection

The installer builds **one input-method backend**, rather than compiling both backends.

* KDE/Plasma desktops use Fcitx5.
* Other desktop environments use IBus.

This is intentional: the installed integration should match the desktop environment rather than installing unnecessary input-method components.

The backend can also be selected explicitly when performing a custom build; see the custom build guide below.

=== What Is Installed

The default installation prefix is:

[source,text]
----
~/.local
----

The main application is therefore installed under the user's home directory rather than a system directory.

For an IBus build, the installer also installs the IBus component description under the user's XDG data directory:

[source,text]
----
$XDG_DATA_HOME/ibus/component/openbangla.xml
----

If `XDG_DATA_HOME` is not set, the usual default is:

[source,text]
----
~/.local/share
----

The installer may configure the user's desktop input sources where supported. It does not modify system-wide input-method configuration.

=== Persistent Build and Cache Data

The fork keeps build state in the user's XDG cache directory so that repeated builds do not have to start from an empty build directory.

The main locations are:

[source,text]
----
$XDG_CACHE_HOME/openbangla-keyboard/
├── build/
└── stage/
----

If `XDG_CACHE_HOME` is not set, `~/.cache` is used.

The build directory contains the CMake/Ninja build state. The staging directory contains the files produced by `cmake --install` before they are copied into `~/.local`.

The default build parallelism is **2 jobs**. It can be changed for a particular invocation, for example:

[source,bash]
----
OPENBANGLA_BUILD_JOBS=4 bash tools/install.sh
----

Use a lower value on systems with limited CPU or memory.

=== Why Use an Isolated Build Environment?

OpenBangla is a native application with C++, Qt, Rust, and input-method dependencies. Building it directly on the host requires the correct development packages for the host distribution.

This fork separates those concerns:

* The host provides the user's desktop session and final runtime environment.
* The isolated build environment provides compilers, headers, CMake, Ninja, Rust, Qt development files, and the selected input-method development files.
* The resulting application is installed into the user's home directory.
* The host package database is not used to install OpenBangla build dependencies.

This is a build strategy, not a containerised runtime requirement. OpenBangla itself runs normally as a user-local Linux application after installation.

== Custom Build Guide

The automated `tools/install.sh` workflow is intended to be the normal path. A custom build is useful when developing OpenBangla, testing a different backend, changing the install prefix, inspecting CMake configuration, or controlling the build steps manually.

The important distinction is that a **custom build still uses the OpenBangla CMake build system**. The fork's installer is an orchestration layer around that build system; it does not replace CMake.

=== 1. Choose the Backend

Enable exactly one backend.

For IBus:

[source,bash]
----
-DENABLE_IBUS=ON
-DENABLE_FCITX=OFF
-DENABLE_BOTH=OFF
----

For Fcitx5:

[source,bash]
----
-DENABLE_IBUS=OFF
-DENABLE_FCITX=ON
-DENABLE_BOTH=OFF
----

Do not enable both for the normal portable/user-local workflow.

=== 2. Configure a User-Local Build

A basic IBus example is:

[source,bash]
----
cmake -S . -B build   -G Ninja   -DCMAKE_BUILD_TYPE=Release   -DCMAKE_INSTALL_PREFIX="$HOME/.local"   -DENABLE_IBUS=ON   -DENABLE_FCITX=OFF   -DENABLE_BOTH=OFF
----

For Fcitx5, change the three backend options to:

[source,bash]
----
-DENABLE_IBUS=OFF -DENABLE_FCITX=ON -DENABLE_BOTH=OFF
----

=== 3. Compile

Build with Ninja:

[source,bash]
----
cmake --build build --parallel 2
----

Increase the parallelism only when the system has enough CPU and memory:

[source,bash]
----
cmake --build build --parallel 4
----

=== 4. Install for the Current User

Install into the configured user-local prefix:

[source,bash]
----
cmake --install build
----

Do **not** use `sudo` for this user-local installation.

If you want to inspect the installation first, use a staging directory:

[source,bash]
----
rm -rf stage
DESTDIR="$PWD/stage" cmake --install build
----

The staged tree can then be inspected before copying it into the final prefix.

=== 5. Clean or Reconfigure

To remove only the CMake build state and configure again:

[source,bash]
----
rm -rf build
----

Then rerun the CMake configuration command.

To rebuild without deleting the build directory:

[source,bash]
----
cmake --build build --parallel 2
----

When changing backend selection, it is safest to use a fresh build directory so that no previous backend configuration remains.

=== 6. Custom Prefix

The installation prefix does not have to be `~/.local`. For example:

[source,bash]
----
-DCMAKE_INSTALL_PREFIX="$HOME/.local/opt/openbangla"
----

However, the portable installer and the desktop integration in this fork are designed around the normal XDG user-local layout. Custom prefixes may therefore require additional desktop/input-method configuration.

=== 7. Build Dependencies

The exact dependency set depends on the selected backend and the distribution providing the build environment.

The automated installer handles the dependency installation inside the selected Toolbox, Distrobox, Podman, or Docker environment. A manual build requires the equivalent development packages to be available in whatever environment you use.

The important categories are:

* C/C++ compiler and standard build tools
* CMake and Ninja
* pkg-config
* Rust and Cargo
* zstd development files
* Qt5 development files
* IBus development files for an IBus build
* Fcitx5 development files for an Fcitx5 build

The installer deliberately installs only the selected input-method development dependency.

=== 8. Updating the Fork

After pulling new source changes:

[source,bash]
----
git pull --recurse-submodules
bash tools/install.sh
----

The persistent build directory allows CMake/Ninja to reuse unchanged build state.

If a source or dependency change causes a stale configuration problem, remove the build cache:

[source,bash]
----
rm -rf "$XDG_CACHE_HOME/openbangla-keyboard/build"
----

If `XDG_CACHE_HOME` is not set:

[source,bash]
----
rm -rf "$HOME/.cache/openbangla-keyboard/build"
----

The fork is experimental, so the build workflow and directory layout may change as development continues.
